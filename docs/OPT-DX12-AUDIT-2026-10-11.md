## 查实并修正的四个问题

### 1. 创建后多等 GPU 完成，放大切换时的原图间隔

修复前 `canFollow()` 必须满足上一份 recording 已经 Evaluate，成功创建的 recording 不满足这个条件。因此，即使创建工作已经实际提交，下一份 recording 仍需等待创建 fence 完成，才允许评估。GPU 在途较深时，可能连续几帧原图。

[Opt 主路径](H:/AgentWorkPlace/DLSS5/_ref/OptiScaler_DLSSNR/OptiScaler/shaders/dlssnr/DlssNr_Dx12.cpp:1795) 明确要求创建帧先提交、后续帧再 Evaluate，原因是同列表创建与评估曾导致 GPU 挂起；其后续帧路径没有额外的 CPU fence 完成门槛。

现在 [pass.cpp](H:/AgentWorkPlace/DLSS5/DLSSNR_LiteDX12/src/nr/pass.cpp:388) 单独标记成功创建的 recording。只有前一 ticket 已实际提交、具有真实 queue/fence、模型与输入形状匹配、后续 recording 能建立提交依赖时，才允许跟进。创建函数仍立即返回，不在创建 recording 内 Evaluate。Pending、Discarded、创建失败和不能确认队列顺序的情况都不能通过这条路径。

现有 `GpuTicket::PrepareSubmission` 保证同队列按先后提交，跨队列在真正 Execute 前等待前驱 fence。本轮没有增加 CPU 等待或新的同步入口，也没有删除跨队列同步。它只缩短额外的创建完成等待；创建帧本身仍可能显示原图，不能称为已实现无缝模型切换。

### 2. 只改模型参数，也销毁整套工作纹理

修复前尺寸、格式或模型 tuning 任一变化都会创建新 Context，丢掉 proxy、answer、output 和转换 guide 纹理，随后重新分配。连续调参会带来额外分配与临时显存占用。

[Opt](H:/AgentWorkPlace/DLSS5/_ref/OptiScaler_DLSSNR/OptiScaler/shaders/dlssnr/DlssNr_Dx12.cpp:1682) 明确只在分辨率改变时更换 scratch，tuning 只重建 feature。

现在 [pass.cpp](H:/AgentWorkPlace/DLSS5/DLSSNR_LiteDX12/src/nr/pass.cpp:537) 将 Context 的尺寸/格式变化与 feature tuning 变化分开；相同尺寸与格式的纹理继续使用。每份 [Recording](H:/AgentWorkPlace/DLSS5/DLSSNR_LiteDX12/src/nr/pass.cpp:140) 额外持有实际使用的 Layer，防止 Context 更换当前 Layer 时，旧 GPU 工作失去自己的 feature 所有权。仍通过真实提交依赖串行使用共享 scratch；无法建立依赖的未完成前驱不允许直接重建跟进。

没有增加每帧纹理分配。节省来自去掉调参时的重复分配，具体毫秒收益未经游戏测量。

### 3. Get 成功但 render subrect 为零，错误地拒绝输入

NGX Get 成功不代表数值非零。修复前 observer 的 `Read(..., fallback)` 仅在 Get 失败时采用 fallback，读取成功的 0 继续进入 `bounded()`，被判无效，整帧 NR 被跳过。

[Opt](H:/AgentWorkPlace/DLSS5/_ref/OptiScaler_DLSSNR/OptiScaler/shaders/dlssnr/DlssNr_Dx12.cpp:2541) 将零尺寸解释为游戏未指定；Dispatch 仅在非零尺寸存在时缩小 guide 的有效范围。

现在 [guide_contract.hpp](H:/AgentWorkPlace/DLSS5/DLSSNR_LiteDX12/src/nr/guide_contract.hpp:18) 对零值先采用创建时的 render 尺寸，创建尺寸也缺失时采用 depth allocation 的剩余有效范围；明确给出的非零尺寸仍按原有规则限制在资源边界内。没有修改 guide 的像素转换或运动矢量算法。

### 4. 局部输出保护缺少尺寸来源

Pass 原本就拒绝处理局部 color output，但观察层只传 Output 的 origin，没有填写 `guides.width[0] / height[0]`。例如 feature 声明输出 1920×1080、实际纹理分配 2048×1080、origin 为零，原有检查会把它当成完整 2048×1080 图像，处理并回写整个 allocation。

现在 [guide_contract.hpp](H:/AgentWorkPlace/DLSS5/DLSSNR_LiteDX12/src/nr/guide_contract.hpp:25) 将创建时的 OutWidth/OutHeight 带入现有验证。局部输出或过大的声明会被拒绝，原图保留；没有添加局部图像处理算法，也没有将错误尺寸静默裁成完整尺寸。

## 仍然存在的风险与限制

| 项目 | 源码结论 | 本轮处理 |
| --- | --- | --- |
| 同一闭合录制未经 Reset，再次 Execute | 严重的条件性生命周期风险。首次 fence 完成后，submitted 项被移除，资源/描述符可能释放或复用；后续 replay 不会延长首次 ticket 的保护 | 按之前要求保留退回后的 ledger，没有重新引入重放修补。不能称为支持安全 replay |
| 四个 pending/submitted 槽 | 达到上限时直接跳过 NR、显示原图，可能交替闪烁；同一列表中的第二次 SR evaluate 也会被 pending 去重拒绝 | 保留原策略。没有证据证明当前游戏在正常版本持续触发它，未扩大池来隐藏问题 |
| 风格切换创建帧 | 主 snippet 必须分开创建录制与评估录制；当前创建帧仍显示原图 | 未通过删除安全间隔来消除。无缝切换需要旧/新模型交接设计 |
| SR-only 捕获 | 当前只登记 feature 1；Opt 还接受 RR feature 13，且资源名可回退 DLSSD.* | 当前工程明示只接游戏 SR evaluate，属于范围差异；本轮没有扩大接入范围 |
| float setter 未验证时的 fallback | 当前保留 Lite 的 slot 1 fallback；Opt 也有 slot 探测，但探测次序不同。无法仅靠静态源码保证未来驱动 ABI | 本轮未改初始化策略；需看实际 runtime 的 setter 验证状态，不能据候选次序差异认定当前闪烁原因 |

Opt 的 feature/resource 保留为 32 次 `TickNrRetired()` 推进，调用点在主 Dispatch 的正常后续处理阶段，不是 GPU 已完成的证明。其 48 个 heap/constant 槽按 dispatch 轮转，也不是 48 帧。因此，照搬 32 或 48 并不能证明闭合列表任意 replay 安全；本轮没有以它们替换 ledger。

## 核对后没有发现新增明确错误的部分

- core Init 与 model Init_Ext 的参数顺序不同，当前 typedef 与实际 Opt/NVIDIA 声明一致；appid `0x24480451`、SDK `0x15`、NR feature ID 18 一致。
- caller 包装函数保留 noinline 和 volatile 返回值，实际模型调用来自包含 `nvngx.dll` 的主体模块，避免 tail call 越过 caller gate。
- preset 包括零值都写入；模型 tuning 在 Create 前写入，并在 Evaluate 前更新参数表；DepthInverted、Reset、MV scale 与各 resource subrect 名称一致。
- 游戏 SR 输出按 UAV 进入，depth/MV 按 NPSR 读取；直接读取、复制和最终回写都恢复游戏资源状态。未知状态没有用猜测替代。
- command guard 对模型/compute 录制暂停自己的绑定捕获，并恢复 heap、root arguments、PSO 和 predication；无法确认绑定或处于 render pass 时跳过。
- 正常单次提交的 recording 保留资源直到真实 fence 完成，Signal 失败不会被当成完成。关闭 NR/释放流后，仍在途的 recording 保留所有权。这些结论不覆盖上述闭合列表 replay。
- GetCapabilityParameters 的销毁责任与本地 NVIDIA SDK 一致；成功初始化的单个 capability map 随 pinned runtime 存活，失败重试销毁旧 map。

这些是源码与构建结论，不是“当前游戏无闪烁、无崩溃”的证明。
