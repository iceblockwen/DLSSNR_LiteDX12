旧修补只按命令列表地址匹配 submitted 项，没有区分 Reset 前后的录制。正常重用同一列表地址也可能被判成重放；在 Execute 前增加的 fence 值会延长旧槽保留。NR 因槽忙而跳过时保留原画，成功时显示 NR，交替发生可造成持续闪烁。日志和代码支持这条原因链，但新版本尚未进行游戏验证。

已移除整个 pre-hook 重放分支及其无用 list 字段。保留原来的四个在途槽、八个拷贝池槽、首次提交后的 Signal 与 fence 回收规则；没有改成 32 帧延迟保留，也没有增加槽数。不能仅凭日志统计声称整个 ledger 与 22:41 的二进制逐字一致。

风格、预设和强度变化仍然需要重建模型。成功 Create 后返回原画。本轮曾参考 `DlssNr_Proxy.cpp` 的 driver proxy 路径尝试同列表 Create 后 Evaluate；随后检查主 snippet 路径 `shaders/dlssnr/DlssNr_Dx12.cpp`，发现该路径明确记录同帧创建和评估曾导致 GPU 挂起，因此已撤回这项尝试，恢复创建帧不评估。后续 Opt 主路径专项复核又去掉了额外的 CPU 创建完成门槛：确认创建实际提交且可建立真实队列依赖后，允许下一份录制评估。创建帧露出原图的问题仍未解决；消除这一帧需要旧/新模型交接，不能删除安全间隔。详见 [Opt DX12 专项报告](H:/AgentWorkPlace/DLSS5/DLSSNR_LiteDX12/docs/OPT-DX12-AUDIT-2026-10-11.md)。

同类模型调参不再额外清空白点测量历史，避免风格变化引起白点回退与测量值跳变；场景 Reset、输入域或 guide 变化的原有重置保留。当前面板已在结束拖动时提交模型强度参数，这部分原本就已修复，本次未重写。

## 其他已修复问题

| 问题 | 后果 | 本次处理 |
| --- | --- | --- |
| 白点测量池依据最近 ticket 推断纹理状态 | 成功提交 A 后，复用录制 B 被丢弃，再复用 C 时会把实际 COPY_SOURCE 错当 UAV | 独立保留已提交状态；丢弃录制不会覆盖它 |
| parked feature 只在下一次 NR Record 中释放 | 关闭 NR 或释放流后，已经安全的模型句柄可能长期残留 | 回收入口及 executor 销毁时也清理；只有完成或明确丢弃的 ticket 才能释放 |
| 失败初始化重试直接丢掉 capability 参数表 | 每次失败后重新开启 NR 都可能漏掉一张表 | 按本地 NVIDIA SDK 说明调用 DestroyParameters；销毁失败保留指针并报告错误 |
| 输入钩子只登记当前线程 | 其他游戏线程可能正在执行被改写的入口 | 改用现有 Detours 事务封装登记其他线程 |
| nativeMutex 内执行捕获恢复 | ReleaseCapture / SetCapture 回调窗口过程，可与 Graphics 锁互相等待或重入 | 捕获恢复在 nativeMutex 解锁后执行 |
| Game 模式缺曝光时仍执行 measured-white GPU 扫描 | Game 分支不会采用该测量值，关闭面板也产生无效工作 | 关闭这条无效测量；Measured、反比曝光读回、面板统计继续按需求运行 |
| Ninja 依赖前缀中文，编译器实际输出英文 | 部分对象头文件依赖变为 0，头文件改动后增量构建可能混用旧布局 | 统一 VSLANG 与依赖前缀，通过 CMake 自带 env 启动编译器，并全量重编所有 C++ 对象 |

capability 参数表的依据：参考工程自带的 NVIDIA `external/nvngx_dlss_sdk/nvsdk_ngx.h` 明确区分 GetCapabilityParameters 与旧 GetParameters；前者由调用方通过 DestroyParameters 销毁。正常成功初始化后的单个参数表随 pinned runtime 保留，不会每帧分配。插件没有替游戏调用 NGX Shutdown。

## 明确保留的风险

真正重复 Execute 同一份未 Reset 的关闭录制时，第一次完成后资源与描述符可能已经被回收或复用。按用户要求退回错误修补，这个风险没有在本次解决；不能称作已支持安全重放。单纯在 post-hook 补 Signal 也必须解决提交与回收之间的窗口、已经退役的录制、Reset 代际识别等问题。

四槽策略在真实 GPU 压力或大量未提交录制下仍可跳帧；该策略保留原图，所以仍可能产生 NR 与原图交替。本次遵照回退要求，没有用扩大池或更长保留期掩盖这一行为。

## 精简度与框架评价

observe → capture → command guard → pass → submission / retirement 的主链清楚，代理与主体分离、shader 预编译、异步日志和配置写入都是合理安排。最需要严谨处理的是“录制、提交、完成、可再次执行”这几种生命周期，不能把一次 fence 完成直接当成关闭列表永久失效。

自有源码没有发现新的编译错误；本次没有做大范围架构重写。pass.cpp 仍较大，但没有为减行数而拆散资源和时序约束。第三方 DX11 backend 文件未进入构建，不产生本插件的每帧开销；兼容入口及 ABI 类型中出现 DX11 也不等于包含 DX11 NR 管线。
