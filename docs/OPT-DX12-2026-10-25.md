# DX12 优化复核报告 — 2026-10-25

参考 [DX11 优化记录](../../DLSSNR_LiteDX11/docs/OPT-DX11-2026-10-25.md)，只读检查当前 DX12 NR 捕获与处理路径，判断仍有哪些优化空间。**本次没有修改代码、配置或部署内容，也没有运行游戏、GPU 跑分或构建。**

## 结论

DX12 已经实现了参考报告中多数适用的优化：兼容资源直读、复制池与工作纹理复用、直接 resolve 的专用路径、相同状态转换跳过、诊断按需启用，以及计时/读回资源的有限池化。没有发现一个既能普遍适用、又能从静态代码确认会明显降低 GPU 毫秒的待办项。

目前最明确的后续候选是**合并每帧资源元数据查询**：捕获入口已检查资源描述和设备归属，`PassExecutor12::Record` 又重复检查；同时状态快照也会读描述。把同一帧已验证的元数据随帧输入向下传，有望减少 CPU 侧 COM 调用，但预计收益有限，需先用 CPU/GPU 帧时间实测确认是否值得改。

因此建议：**先测量，不先改 GPU 管线**。图像预处理/resolve dispatch、资源状态和输入不可变性均牵涉模型契约或正确性；在没有基准数据前，不建议通过合并 pass、削减复制或放宽状态检查来追求理论收益。

## 对照结果

| DX11 参考项 | DX12 当前状态 | 结论 |
|---|---|---|
| 输入元数据只读一次并向下传 | `Capture12` 获取资源描述/归属后，`PassExecutor12::Record` 再次执行 `GetDesc` / `GetDevice` 检查；状态发布也读取描述 | **尚有低风险 CPU 优化候选**：传递已验证的帧级元数据；保留边界校验，先测开销 |
| 指针相等快速判断 | 捕获 ledger 以命令列表的 COM `IUnknown` identity 关联待提交记录；资源复制池按描述复用 | 已存在适当的身份/描述复用机制；没有证据显示这里是热点 |
| 常量资源只初始化一次 | NR 输入没有与 DX11 常量零 MV 同构的每帧上传；白点和计时读回使用受限池 | 未发现可直接迁移的常量上传优化 |
| 不用资源不创建 | debug 资源读取按当前视图/面板状态门控；meter 只在曝光测量或统计需要时记录；timestamp 只在面板可见时启用 | 已按需执行；不是无条件逐帧路径 |
| 模式收敛为构造期常量 | `DirectResolve` / `SkipSmallSwapchains` 由 INI 在初始化时读取并缓存；常规捕获按运行设置决定是否处理 | 已存在进程级缓存策略，且不再判断进程名 |
| 日志/诊断避免常规路径开销 | 面板计时和 debug capture 有显式需求门控；GPU timing 资源上限为 8，满时不等待 GPU | 已有保护；不建议为优化删去仍被 UI/测量功能使用的诊断 |
| 简单深度候选排序、深度尺寸与 subrect 护栏 | DX12 不做 DX11 原生深度候选捕获；由游戏 NGX 提供 guides，并检查 region 边界 | 不适用；不可把 DX11 专有捕获策略移植过来 |
| 避免多余中间纹理 | 符合 shader view 条件的输入直接读取；只复制需转换/诊断的输入；复制仅覆盖 mip 0；同描述复制资源可复用 | 核心路径已优化 |
| 输出直写 | 普通路径使用可写 scratch 并回写；Death Stranding 有独立策略，把结果直接写回原 UAV，并为模型保留不可变输入副本 | 已有受限实现，不应无条件推广；目标资源和输入不可变约束不同 |
| 状态转换只在状态变化时发 | `Transition` / `TransitionSubresource` 在资源为空或 `before == after` 时直接返回 | 已实现 |
| descriptor / PSO 池化 | PSO/root signature 按 executor 缓存；Recording 描述符堆随提交保留，完成后复用；不在 GPU 尚未完成时覆盖 | 已有缓存与安全复用，不是显而易见的逐帧重复创建缺陷 |
| GPU timing 只在诊断时创建 | NR timestamp 由面板可见状态驱动，并通过上限为 8 的 pool 管理 | 已实现 |
| 分辨率/格式稳定时复用资源 | proxy、answer、resolve 和 guides 随 Context 复用；捕获复制资源按描述池化，重建只在描述变化时发生 | 已实现 |
| 特定深度格式族的转换 | depth/motion 的 view format 有转换映射；仅不匹配模型工作格式或需翻转时才录制 guide 转换 | 已有按需转换；无依据进一步删减 |

## 实施跟进 — 2026-10-25

已按第 1 项合并帧级资源元数据：

- NGX observer 在解析 guides 时读取每个输入资源的描述，并将 frame-scoped metadata 随 `FrameInput` 传入捕获层。
- 捕获层继续校验游戏资源的设备归属、类型、状态和 subrect；直读资源与复制资源分别记录实际交给 pass 的描述。需要兼容缺少 metadata 的输入时，捕获层仍会读取描述作为回退。
- NR pass 复用这些描述完成输入校验、格式/尺寸状态、前后帧 guide 对比、resolve 目标检查和 descriptor 格式选择；资源设备归属由捕获层验证一次。预览也复用该帧的描述。
- exposure texture 仍由捕获层单独检查；optional white meter 继续执行自身的资源/设备校验。

验证：`litedx12_frames` 与 `litedx12_runtime` 的 Windows x64 Release 编译、链接通过。未运行游戏、GPU profiler 或帧时间对比，因此只确认实现与构建正确，不宣称已测得性能提升。

## 日志与诊断整理 — 2026-10-25

按 [DX11 优化记录 §1.7](../../DLSSNR_LiteDX11/docs/OPT-DX11-2026-10-25.md) 的日志/诊断条目复核并整理 DX12：

- **等级语义**：与 DX11 相同的 `[Diagnostics] Level`（`Detail` 枚举、`DetailLevel()`）：`0` 不建文件、不拼接日志字符串；`1` 只记录启动、失败与状态变化；`2` 输出额外 verbose 诊断（如 NR 层创建）。插件不再有任何调试器输出（`OutputDebugString`）路径，`[General] Debug` 已删除；诊断只有日志文件一个通道。缺少 `Level` 时继续读取旧的 `[General] Log=0/1`，这是相对 DX11 唯一的兼容差异；格式化统一走 `LogFormat(level, ...)`，比 DX11 的手写 `if (DetailLevel()...)` 更不容易漏掉 Off 门控。
- **每进程重写**：主日志与代理 bootstrap 日志都改为 `w`，不再跨会话累积；`Level=0` 时不写文件。
- **日志位置**：跟随当前生效的配置目录；游戏目录不可写时回退到配置已使用的用户档案目录，探针失败才回退，避免只读安装下完全没有日志。启动头部记录日志与配置路径。
- **避免 Off 时格式化**：新增 `LogFormat(level, ...)`；所有带格式化的日志点改为先判等级再 `swprintf`。`ReportRejectedResource` 在 Off 时直接返回。
- **单一等待原因写入者**：面板不再调用 `ReportModelWait`（此前面板与管线会交替写入等待原因），改为在面板内本地显示等待文本；日志仍由管线状态变化写入。
- **队列饱和不再静默**：日志队列满 4096 行后计数，恢复时补一行丢弃统计。
- **状态/路径诊断**：`NR route` 只在模型/调试/解析目标/输入直读与复制组合变化时输出一次；复制池重建时输出尺寸、格式与标志，便于确认资源churn。首次观察到游戏 NGX SR/RR evaluate 及 feature release 各记一行，面板等待原因仍由管线统一写入。
- **计时口径**：面板 GPU timing 的提示改为明确"最近完成的一帧录制，含 guide 转换/白点/encode/模型/resolve，不含 feature 创建与游戏自身队列工作"，避免把不同 API 的未校准区间直接相减。
- **其他修正**：`Report` 不再在持有状态锁时写日志；成功路径每帧少一次 `PassStatus` 快照；空日志行不再写入。

### 复核发现并处理的问题

| 问题 | 处理 |
|---|---|
| 日志以追加模式跨会话增长 | 改为每进程 `w` |
| `[General] Log=0` 无法关闭代理 bootstrap 日志、也无法表达 verbose | 统一 `Diagnostics.Level` + 旧键回退 |
| Level 关闭时仍有 `swprintf_s` 格式化成本 | 引入 `LogFormat`/`LogVerbose` 并改所有格式化点 |
| 面板与管线同时写 wait reason，字符串交替会放大日志 | 面板只显示，不写日志 |
| `Report` 持有状态锁时调用日志 | 移到锁外 |
| 只读游戏目录没有日志 | 跟随配置目录并回退用户档案目录 |
| 每帧两次 `pass->Snapshot()` | 合并为一次 |

未改动：GPU timing/白点测量/预览仍按面板/测量需求门控；DX11 的 Present 延迟测量与深度候选/桥接诊断不适用于 DX12。本轮只验证 Release 与 Release-HDR 编译安装，未运行游戏或 GPU profiler。

## 对比 / DebugView 移除与诊断收敛 — 2026-10-25

按当前使用范围删除仅用于人工比对的展示路径，保留 `Apply NR result`、最终 `Difference gain` 与 Resources 页的三张预览：

- 移除 `Compare`（并排/擦除）、`Split`、`Zoom`、`Swap sides`、`NR debug view`、`Debug scale` 及其 INI 键；`Apply NR result` 单独保留，见下一条。
- 保留 `Apply NR result`（`[NeuralRendering] ApplyModel`）。与 DX11 的展示开关不同，这里是真 bypass：关闭时模型仍 evaluate 以保持历史和白点测量，但直接跳过 resolve 和 color 拷回，游戏原帧完全不变。
- `MaxRatio` 不再作为设置/INI/常量：shader 内固定 `MaxLuminanceRatio=16`。`Compose` 路径（Preserve HDR highlights）在色度重建时限制编辑比例，非 Compose 路径限制模型输出亮度；`DifferenceGain` 之后不再做额外的最终亮度钳制。
- 非 HDR（`sceneLinear=false`，`display=1`）路径本来就不做曝光/映射：encode 直接写 `max(color.rgb,0)` 和原 alpha，resolve 不做 sRGB/Decode、`norm=1`、白点为 1；面板显示 `non-HDR bypass: no exposure/encoding`。
- `lite_color.hlsl` 删除比较采样、debug 模式和 `applyModel` 分支；解析路径简化为固定像素采样，常量块由 24 个 DWORD 缩到 16 个，descriptor 堆由 30 降到 24，根签名不再需要采样器。
- 清理无消费者的诊断字段：`PassStatus::timedPasses/gameExposureScalar/whiteMeasurementPending`、`GameDlssStatus::evaluations`、`DebugStatus::state/api/source/view`、`GraphicsStatus::api/queueCaptured`、`Status::verbose/logging`，以及 `[Diagnostics] ResourceView` 和启动时的 `nr::Configure(View)`。`ResourceScale`、`DepthContrast`、`DepthUpsideDown` 仍被预览/深度翻转使用，保留。
- 面板等待原因、日志等级和 Resources 预览保持不变。

模型 mask 输入复核：与 DX11 相同，在 `Create` 与每次 `Evaluate` 前都显式写 `DLSSNR.ControlMask = nullptr`（[DX11 pass.cpp 571/794](../../DLSSNR_LiteDX11/src/nr/pass.cpp)）。这一步必须保留：能力参数块会跨 create/evaluate 复用，清空可防止旧指针残留；本工程中没有其他 `ControlMask` 写入点，`DLSSNR.UseAutoMask` 是唯一 mask 开关。

## 兼容策略改由 INI 驱动 — 2026-10-25

- 删除 `ds.exe` / `GTA5_Enhanced.exe` 的进程名判断。
- `[Diagnostics] DirectResolve=0`：开启后 NR 把 Color/Depth/MV 复制为不可变输入，并把结果直接 resolve 到捕获颜色 UAV；要求该颜色有 UAV 且当前为 `UNORDERED_ACCESS`。仅应在确认资源契约的游戏上开启。
- `[Diagnostics] SkipSmallSwapchains=0`：请求/实际宽或高小于 100 的交换链不包装；旧键 `GtaSkipSmallSwapchains` 在缺少新键时作为兼容别名读取。
- DirectResolve 的 resolve 目标已经是 UAV，输出后不再做 `UAV→SRV→UAV` 的空转；私有输出路径仍需要 `UAV→SRV` 供拷回读取。
- 启动日志会分别记录两个开关是否开启。

## 建议的下一步（若要继续优化）

1. **先建立基线**：在目标游戏固定分辨率、场景和设置下记录 CPU frame time、NR GPU timing、是否启用 panel/debug/Measured white，并重复采样。当前代码检查只能证明工作存在或被门控，不能证明哪项占用显著。
2. **优先验证元数据合并的收益**：比较采集入口与 pass 内重复的每帧 `GetDesc` / `GetDevice` 调用；若 CPU profiling 能观测到成本，再考虑把已验证的尺寸、格式、owner 信息随帧传递。不得因复用缓存而跳过资源身份、设备归属或 subrect 验证。
3. **单独测量条件路径**：如启用 `Measured` white，meter 会以 `WhiteEvery` 周期执行 GPU 测量；面板统计也会请求测量。只应在用户不需要对应测量时关闭它，不能默认视作无用工作。
4. **保持游戏专用直写范围**：当前 Death Stranding 的 immutable-input / 原 UAV resolve 路径是兼容性策略，不是通用低复制方案。没有逐游戏验证前，不建议扩大作用范围或改变输出顺序。

## 不建议的无测量改动

- 为减少一份 texture，直接让模型输出覆盖仍需读取的输入；这会破坏输入不可变性。
- 移除格式转换或 depth flip；模型输入格式/方向契约可能改变。
- 删除读回、面板计时、预览或测量路径；它们是用户可见诊断功能，应按需门控而非整体删除。
- 仅凭 `CreateCommittedResource` / barrier / descriptor API 调用的源码数量，推断为 GPU 瓶颈。当前工作纹理和描述符已有生命周期与复用策略；需用 profiling 区分 CPU 录制、GPU dispatch、带宽与同步成本。
